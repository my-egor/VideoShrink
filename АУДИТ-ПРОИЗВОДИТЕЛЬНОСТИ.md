# Аудит и оптимизация производительности VideoShrink 1.1.4 → 1.1.5

## 1. Общая оценка проекта

Главная потеря времени — обязательное перекодирование каждого нового поддерживаемого MP4 на CPU в H.265 lossless с пресетом `veryslow`. Это касается обоих режимов. Размер входного файла отражает степень уже выполненного сжатия. Для времени важнее количество и разрешение кадров, их сложность, пресет и оборудование. У найденной копии ролика на 62 843 587 байт 1 789 кадров H.264, 1080×1920, 30 кадров/с, 59,63 с, звук AAC. Lossless сохраняет декодированные кадры исходника, но может дать файл существенно больше исходного H.264.

Проверены интерфейс Tkinter, очередь и отмена, команды FFmpeg/FFprobe, проверка качества, SQLite, JSON-отчёт, настройки, README, тестовые сценарии, комплектование PyInstaller, установщики NSIS/Inno Setup и скрипты подготовки зависимостей. Обработка локальная, без API, оплаты и сетевого трафика. Сеть нужна при подготовке сборочных зависимостей. Фоновая очередь, сохранение во временный файл, публикация без перезаписи и повторное использование завершённого результата — полезные механизмы.

Старый лог 1.1.1 для одноимённого файла содержит настройки x265, но не причину сбоя. В доступной локальной папке 1.1.4 нет лога описанного пользователем запуска. Поэтому показанные 42 минуты — сообщённый прогноз интерфейса, а не измеренная длительность. Для KB прямых материалов по FFmpeg не найдено.

### Контрольный замер

Поставляемый FFmpeg, первые 60 кадров найденного ролика, один прогон каждого пресета последовательно, одинаковый формат yuv420p и lossless H.265, без аудио, с MP4 faststart. Время включает кодирование и запись, но проверка хешей кадров выполнялась отдельно. Файлы замера создавались во временном каталоге.

| Пресет | Время | Размер фрагмента | Декодированные кадры |
|---|---:|---:|---|
| fast | 3,59 с | 24 427 474 байта | 60 хешей совпали с источником |
| medium | 11,17 с | 18 396 562 байта | 60 хешей совпали с источником |
| veryslow | 123,95 с | 17 319 093 байта | 60 хешей совпали с источником |

На этом фрагменте `medium` был примерно в 11 раз быстрее `veryslow` при увеличении размера кандидата на 6,2%. `fast` был примерно в 35 раз быстрее при увеличении размера на 41%. Ускорение относится к измеренному фрагменту, а размер сравнивается с результатом `veryslow`, поэтому цифры не означают уменьшения исходного файла. Для полного файла и других компьютеров нужен отдельный замер. В документации x265 также показан компромисс между временем и размером при неизменных кадрах. [x265 lossless](https://x265.readthedocs.io/en/master/lossless.html), [пресеты x265](https://x265.readthedocs.io/en/stable/presets.html).

## 3. Быстрые улучшения с высокой отдачей

Сначала заменить `veryslow` на измеренный рабочий пресет, проверять размер кандидата перед полным декодированием, перестать выдавать выросшие файлы за сжатые и уважать настройку повторов. Эти изменения затрагивают главным образом `core.py` и несколько статусов очереди. Параллелизация очереди и настройка интерфейса уступают им по ожидаемому эффекту.

Для профиля без потерь подтверждать исходные кадры на тестовом наборе хешами, а звуковые дорожки и метаданные проверять отдельно. Проверка длительности и разрешения сама по себе не доказывает побитового совпадения.

## 4. Текущий и предлагаемый процессы

| Сценарий | Сейчас | Предлагается |
|---|---|---|
| Повторный запуск | Отпечаток, поиск выходного пути и несколько обращений к SQLite | Стабильный снимок, один поиск подтверждённого результата с версией профиля. При попадании сразу вернуть статус |
| Строго без потерь | Анализ → полное `veryslow` → полное декодирование → проверка лимита → публикация | Анализ → быстрый lossless в пределах бюджета → ранний отказ при доказанном превышении → проверка только пригодного кандидата → атомарная публикация либо статус «исходник сохранён, уменьшение не получено» |
| Режим до 2 ГБ | Полное lossless и его декодирование → при превышении два прохода `slow` → повторы при размере → декодирование и VMAF | Lossless в бюджете → при необходимости и разрешении пользователя кодирование под размер → контроль полного результата. Если исходник уже ниже лимита, по умолчанию сохранять его при неудаче lossless. Это уточнение поведения согласовать в спецификации режима |
| Задача «сделать заметно меньше при близком качестве» | В текущих двух режимах потери разрешены только по условию лимита | Если нужен этот сценарий для роликов меньше 2 ГБ, предложить отдельный явно выбранный профиль. Сравнить однопроходный CRF с контролем размера и качества. При жёстком целевом размере двухпроходный ABR оставить кандидатом |

`-c copy` пригоден, если нужна быстрая смена контейнера или копирование дорожек. Он оставляет видеоданные с тем же битрейтом и сам по себе почти не уменьшает уже сжатый MP4. `-fs` умеет прекратить запись, но такой результат может оказаться усечённым и должен отбрасываться. CRF задаёт качество и оставляет размер переменным, двухпроходный ABR полезен для целевого объёма. [FFmpeg](https://ffmpeg.org/ffmpeg.html#Streamcopy), [HandBrake о качестве и битрейте](https://handbrake.fr/docs/en/latest/technical/video-cq-vs-abr.html).

## 5. Архитектурные улучшения

- Сохранить Tkinter, FFmpeg и SQLite. Добавить выбор маршрута перед кодированием и единый исполнитель стадий с контролем бюджета и отменой. Избегать повторов проверок, сохраняя их гарантии. Для VMAF сначала измерить многопоточность. Выборочные кадры использовать только для предварительной оценки, если итоговый порог по-прежнему требует проверки всего ролика. [Документация libvmaf в FFmpeg](https://ffmpeg.org/ffmpeg-filters.html#libvmaf).
- Проверить Intel Quick Sync, NVENC и AMD AMF как опциональные пути для сжатия с разрешёнными потерями. Имена всех трёх кодеров есть в поставляемом FFmpeg. Наличие устройства, драйвера, фактическая скорость и качество не установлены. Нужен пробный запуск, CPU-путь при недоступности, проверка размера, качества и совместимости. Наличие аппаратного кодера само по себе не оправдывает изменение lossless-режима. [NVIDIA SDK](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/ffmpeg-with-nvidia-gpu/), [HandBrake Performance](https://handbrake.fr/docs/en/latest/technical/performance.html).
- При подтверждённой цене повторов хранить проверенные промежуточные артефакты с отпечатком входа, версией FFmpeg, параметрами и ограниченным сроком жизни. Возобновлять с границы завершённого этапа. Возобновление с произвольного кадра и параллельное кодирование вводить только при доказанной выгоде: они усложняют синхронизацию, управление битрейтом и нагрузкой на CPU и диск.

## 7. Ожидаемые результаты и измерение

Полные прогоны проводить на одном компьютере и с одним FFmpeg, без параллельных кодирований, по три повтора на вариант. Набор включает этот ролик, динамичное и зернистое видео, длинный файл около 2 ГБ, несколько аудиодорожек, VFR, испорченный файл и искусственно низкий лимит для проверки fallback. Отдельно проверить чистый запуск portable и установщика.

Записывать медиану времени всего задания и стадий, fps, итоговый размер, объём временных файлов, число запусков FFmpeg и повторов, пиковую память, CPU-время, результат проверки кадров или VMAF и ошибку ETA на 25%, 50% и 75% работы. Для восстановления замерять время от перезапуска до готового результата и число повторно запущенных стадий. Сравнивать время вместе с размером и долей успешных результатов, чтобы быстрые отказы не выглядели как ускорение успешного сжатия.

Критерии выпуска: меньше времени на успешный результат и на отказ от невыгодного кандидата, ноль сохранённых файлов больше исходника для операции «сжать», совпадение кадров в строгом режиме и соблюдение заданных качества и лимита в усиленном. Фактический выигрыш полного файла и аппаратного пути предстоит подтвердить.

## 8. Реализация и измерение версии 1.1.5

В `core.py` lossless-пресет сменён с `veryslow` на `medium`. FFmpeg контролируется по фактическому размеру незавершённого файла. Когда он достигает исходного размера, процесс завершается, временный файл удаляется, а приложение пишет отдельный статус «Размер не уменьшится; остановлено». В режиме 2 такой ранний выход запускает lossy-ветку, только когда исходник уже достигает лимита 2 ГБ. Если исходник меньше лимита, повторное кодирование с потерями не запускается. Параметр `size_retries` теперь напрямую ограничивает повторы, вместо принудительного минимума в три. В ключ обработки добавлен lossless-пресет, чтобы история старой версии не возвращала прежний результат как актуальный.

| После, lossless `fast`, полный контрольный кандидат | 178,63 с | 856 371 943 байта | да, все 1 789 | 13,6× размера исходника |
| После, lossless `medium`, полный контрольный кандидат | 338,26 с | 581 436 205 байт | да, все 1 789 | 9,3× размера исходника |
| После, выбранный `medium`, ранняя остановка приложения | 29,03 с | неполный файл удалён | кодирование было остановлено по размеру, кадры частичного файла не использовались | статус `NO_REDUCTION`; исходник совпадает по размеру и времени изменения |

Полный прогон старого `veryslow` до конца не делался: уже незавершённый кандидат стал больше источника. Оценка полной длительности старого варианта экстраполирована из показываемой скорости FFmpeg, а не измерена завершённым прогоном. Полные времена и размеры `fast`/ `medium` относятся к этому компьютеру и включают запись MP4 с faststart. Для этого файла `medium` выбрано потому, что оно даёт на 32,1% меньший lossless-кандидат, чем `fast`, а новый предел размера завершает бесполезное кодирование за 29,03 секунды.

### Проверки реализации

- 15 модульных проверок прошли, включая размерный предел, режим без уменьшения, fallback и точное число повторов.
- Полное сравнение хешей всех кадров прошли полные кандидаты обоих пресетов.
- Реальный вызов нового кода на полном ролике вернул `NO_REDUCTION` за 29,03 секунды. Исходник остался нетронутым, временный выход удалён.
- Установщик и переносимая сборка 1.1.5 собираются после финальной проверки PyInstaller.

Ограничение режима 1 по результатам этого замера: уже сжатый lossy H.264 нельзя перекодировать в строгий lossless H.265 и одновременно обещать уменьшение файла. Для уменьшения такого источника нужна явно разрешённая потеря качества. Пресет `fast` обрабатывает быстрее, но на этом ролике создаёт заметно больший результат, поэтому для задачи минимального lossless-размера выбран `medium`.
